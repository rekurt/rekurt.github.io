# Rekurt Portfolio Hub — архитектурная спецификация

## 1. Цель

Создать отдельный публичный репозиторий `rekurt/rekurt.github.io` и статический сайт
`https://rekurt.github.io`, который одновременно служит:

- продуктовым каталогом собственных open-source проектов;
- техническим портфолио автора;
- центральной точкой входа в сайты, документацию, исходный код и релизы;
- автоматически обновляемым реестром всех публичных репозиториев профиля `rekurt`.

Сайт не копирует runtime-сервисы и не становится монорепозиторием всех продуктов. Он
агрегирует проверяемые публичные данные GitHub, дополняет их кураторскими метаданными и
публикует неизменяемый статический артефакт.

## 2. Проверенное исходное состояние

До создания portfolio hub, на 5 сентября 2026 года, профиль `rekurt` содержит 49 публичных
репозиториев:

- 19 оригинальных репозиториев;
- 30 GitHub-форков;
- 6 доступных собственных GitHub Pages: `chislo`, `maccoffee-dist`, `openkline`,
  `openkline.tech`, `vpn-hub`, `Mac-Coffee`;
- 3 доступные страницы API-документации на `pkg.go.dev`: `go-propisyu`,
  `gost-crypto`, `ymsdk`;
- страница пакета `prt` на `crates.io` заявлена как homepage, но автоматический HTTP-клиент
  получает защитный ответ `403`, поэтому ссылка отображается без утверждения о доступности.

Ссылки homepage у простых форков считаются ссылками исходных проектов, а не сайтами автора.

## 3. Аудитория и позиционирование

Основная аудитория — пользователи продуктов и open-source разработчики. Вторичная —
работодатели, заказчики и технические руководители.

Позиционирование автора: backend-разработчик и архитектор, создающий практичные инструменты
для fintech/crypto, developer tooling, системной автоматизации и прикладных SDK. Главная
страница сначала отвечает на вопрос «что можно использовать», затем — «кто и как это
создаёт».

Язык интерфейса по умолчанию — английский для международной доступности. Полная русская
локализация имеет равноправные URL под `/ru/`. Названия проектов, команды установки и API
не переводятся.

## 4. Правило отбора и продуктовая модель

После создания `rekurt.github.io` общий реестр будет содержать не менее 50 репозиториев:
49 исходных и сам системный репозиторий portfolio hub.

Сайт содержит два представления.

### 4.1. Продуктовый каталог

В каталог входят оригинальные проекты и существенно переработанные поддерживаемые форки.
Связанные репозитории объединяются в один продукт, чтобы дистрибутив, Homebrew tap и
адаптеры не выглядели независимыми продуктами.

Начальный каталог содержит 14 продуктов:

1. `chislo`;
2. `cortex-forge`;
3. `dbdiff`;
4. `depth`;
5. `git-barber` + формула из `homebrew-tap`;
6. `gitlab-downloader`;
7. `go-propisyu`;
8. `gost-crypto`;
9. `Mac-Coffee` + `homebrew-maccoffee` + `maccoffee-dist`;
10. `openkline` + `openkline-react` + `openkline-vue` + `openkline.tech`;
11. `prt`;
12. `sprint-velocity`;
13. `vpn-hub`;
14. `ymsdk`.

`Mac-Coffee` показывается как продукт с явной ссылкой и атрибуцией upstream
`Elliotwu-7/Mac-Coffee`. `tsql` не считается авторским продуктом: его README и ссылки
атрибутируют `fcoury/tsql`; он остаётся в полном реестре как форк.

### 4.2. Полный реестр

Страница `/registry/` показывает все обнаруженные публичные репозитории, включая сам
portfolio hub, и явно маркирует:

- original;
- maintained fork;
- fork/mirror;
- support/distribution repository;
- archived, если статус появится позднее.

Реестр не скрывает репозитории, но не приписывает авторство upstream-кода владельцу форка.

## 5. Информационная архитектура

- `/` — hero автора, ключевые направления, featured-проекты, последние релизы и ссылка на
  полный каталог;
- `/projects/` — фильтруемый каталог по домену, языку и типу;
- `/projects/<slug>/` — описание продукта, статус, версия, сайты, документация, установка,
  связанные репозитории, лицензия и выдержка из актуального README;
- `/registry/` — полный технический реестр публичных репозиториев;
- `/about/` — профиль автора, инженерные принципы и стек;
- `/ru/...` — русские варианты тех же страниц;
- `/404.html` — статическая страница ошибки с навигацией к каталогу.

Каждая карточка всегда различает четыре действия: `Website`, `Documentation`, `Source`,
`Release`. Несуществующие действия не отображаются.

## 6. Репозиторий и компоненты

Репозиторий имеет две изолированные части.

### 6.1. Go-синхронизатор

Команда `cmd/catalog-sync` отвечает только за получение и нормализацию данных. Основные
пакеты:

- `internal/githubapi` — REST/GraphQL-клиент с ETag, таймаутами и ограничением параллелизма;
- `internal/catalog` — модель продукта, репозитория, релиза и ссылки;
- `internal/sync` — discovery, merge с кураторским манифестом, валидация и генерация;
- `internal/markdown` — безопасная подготовка README и переписывание относительных ссылок.

Синхронизатор читает `catalog/projects.yaml` и генерирует детерминированные файлы в
`site/src/data/generated/`. Сеть не используется во время обычного рендера Astro.

### 6.2. Astro-сайт

`site/` — статический Astro-проект на TypeScript. Он читает только валидированный snapshot,
создаёт страницы при сборке и не требует runtime API, базы данных или serverless-функций.
Небольшие фильтры каталога работают на vanilla TypeScript после загрузки страницы.

Разделение позволяет тестировать GitHub-интеграцию независимо от UI и воспроизводимо
пересобирать сайт из зафиксированного snapshot.

## 7. Источники данных и схема управления

`catalog/projects.yaml` — единственный кураторский источник. Для продукта задаются:

- стабильный `slug`;
- основной и связанные репозитории;
- тип и домен;
- порядок и featured-флаг;
- краткие EN/RU-тексты;
- явные overrides для сайта, документации и установки;
- атрибуция upstream для maintained fork;
- причины исключения из продуктового каталога.

GitHub является источником изменяемых фактов: visibility, fork/upstream, topics, язык,
лицензия, default branch, timestamps, latest release/tag, README и Pages/homepage.

При конфликте факт GitHub не переписывается кураторским текстом. Override допускается только
для презентационных полей и группировки.

Новый оригинальный публичный репозиторий автоматически появляется в `/registry/` и в отчёте
`catalog-sync check`. В продуктовый каталог он попадает после одной записи в YAML. Форки по
умолчанию остаются только в реестре; включение требует явного `maintained_fork: true` и
upstream-атрибуции.

## 8. Синхронизация документации и версий

Workflow `sync-catalog.yml` запускается:

- каждый час по расписанию;
- вручную через `workflow_dispatch`;
- при изменении манифеста или кода синхронизатора.

Алгоритм:

1. получить все публичные owned repositories пользователя;
2. обогатить их releases, tags, Pages/homepage и README;
3. объединить с `projects.yaml`;
4. проверить уникальность slug, валидность URL, upstream-атрибуцию и связи;
5. подготовить безопасный Markdown и нормализованный JSON;
6. сравнить результат с текущим snapshot;
7. при изменении создать conventional commit `chore(catalog): sync project metadata`;
8. запустить проверку и deployment через обычный push.

Почасовой polling выбран вместо distributed webhook: дочерним репозиториям не нужны PAT,
GitHub App или дополнительные workflow. Допустимая задержка обновления — не более 70 минут.
Позже webhook можно добавить без изменения модели данных.

Версия продукта определяется в порядке: latest non-draft GitHub Release, последний SemVer
tag, версия manifest-файла (`Cargo.toml`, `package.json`) только как информационный fallback.
`go.mod` не содержит версии модуля, поэтому для Go fallback после SemVer tag отсутствует.
Дата последнего материального изменения snapshot и источник версии сохраняются явно; пустой
почасовой check не меняет timestamp и не создаёт коммит.

README фиксируется вместе со SHA исходного commit. Относительные ссылки и изображения
переписываются на raw/blob URL этого SHA, поэтому опубликованная документация не меняется
между сборками незаметно.

## 9. Дизайн-система

Визуальный язык продолжает сильные стороны `openkline`: dark-first интерфейс, тонкая сетка,
моноширинные числовые данные и высокая информационная плотность, но остаётся нейтральным для
нефинансовых продуктов.

Базовые решения:

- фон graphite, поверхности slate, основной accent cyan, status accent emerald;
- sans-serif для текста, monospace для версий, команд и метрик;
- 4/8 px spacing scale, 1 px hairline borders, умеренные радиусы;
- карточки без декоративных 3D-эффектов и тяжёлых теней;
- motion только для раскрытия, фильтра и focus feedback; учитывается
  `prefers-reduced-motion`;
- WCAG 2.2 AA для контраста, keyboard navigation, skip-link, видимый focus и корректная
  семантика заголовков;
- responsive layout от 320 px, основные breakpoints 640/960/1280 px.

Компоненты: header, language switcher, project card, status/version badge, filter bar,
repository table, release timeline, code/install block, link group и footer. Все цвета,
типографика, spacing и motion задаются CSS custom properties.

## 10. Безопасность и обработка ошибок

- GitHub token используется только в Actions, имеет минимально необходимый read-доступ и не
  попадает в статический output;
- HTML из README не исполняется: применяется allowlist sanitizer;
- `javascript:`, data-HTML и неизвестные URL-схемы удаляются;
- внешние ссылки получают безопасные `rel`-атрибуты;
- sync использует таймауты, retry с backoff и GitHub rate-limit headers;
- частично полученные данные не публикуются: snapshot заменяется атомарно только после полной
  валидации;
- при временной ошибке остаётся последняя валидная версия сайта, а workflow завершается с
  ошибкой;
- секреты и приватные репозитории запрещены инвариантами модели и тестами.

## 11. CI/CD и релизы

Pull request workflow выполняет:

- `go test ./...`, `go vet ./...`;
- проверку форматирования Go;
- unit и fixture-тесты синхронизатора;
- ESLint/TypeScript/Astro checks;
- production build;
- проверку внутренних ссылок и smoke-тест HTML;
- accessibility smoke-тест ключевых страниц.

`deploy-pages.yml` публикует `site/dist` через официальный GitHub Pages artifact flow после
успешной проверки `main`. Environment `github-pages` получает URL deployment.

Dependabot обновляет Go modules, npm и GitHub Actions еженедельно. Release Please ведёт
CHANGELOG и SemVer самого portfolio hub. Версии продуктов остаются независимыми и
агрегируются sync-процессом.

## 12. Тестирование и критерии готовности

Готовность доказывается следующими проверками:

- все 49 исходных публичных репозиториев и новый `rekurt.github.io` присутствуют в snapshot
  и `/registry/`; новые публичные репозитории не требуют изменения тестовой константы;
- 14 продуктовых сущностей корректно связывают зависимые репозитории;
- maintained fork содержит видимую upstream-атрибуцию;
- версии и README совпадают с GitHub SHA, записанным в snapshot;
- шесть известных Pages URL исходных проектов проверяются и отображаются как websites, а
  корневой URL portfolio hub проверяется отдельно после deployment;
- package documentation не смешивается с product websites;
- EN/RU страницы существуют и имеют корректные alternate links;
- сборка детерминирована на одинаковом fixture input;
- нет битых внутренних ссылок, утечки секретов и ссылок на приватные репозитории;
- desktop и mobile screenshots проходят визуальную проверку;
- production deployment отвечает HTTP 200 на `/`, `/projects/`, `/registry/` и `/ru/`.

## 13. Этапы поставки

1. Создать репозиторий, базовые quality gates и зафиксировать исходный аудит.
2. Реализовать Go-модель, fixtures и детерминированный sync.
3. Добавить кураторский manifest и полный generated snapshot.
4. Реализовать дизайн-систему и EN/RU страницы Astro.
5. Добавить тесты, link/accessibility checks и GitHub Actions.
6. Создать `rekurt/rekurt.github.io`, запушить `main`, включить GitHub Pages и проверить
   production URL.
7. Выполнить финальный аудит всех требований и опубликовать отчёт.

## 14. Принятые ограничения

- первая версия не использует backend, базу данных, Cloudflare Worker и distributed webhook;
- сайт не редактирует дочерние репозитории;
- полные README простых форков не републикуются;
- пользовательская аналитика и cookies отсутствуют;
- собственный домен не требуется: канонический адрес первой версии —
  `https://rekurt.github.io`.
